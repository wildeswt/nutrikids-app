# Feeding Logs (RF-06) and Educational Content (RF-18)

Backend for NK-39 and NK-40. The screens that consume them are NK-53 (feeding) and NK-54 (_Aprende en casa_).

Code: `src/services/feedingLogs.service.ts`, `src/services/education.service.ts`, `src/routes/children.routes.ts`, `src/routes/education.routes.ts`, `src/lib/seedEducation.ts`; schemas in `packages/shared/src/schemas/feedingLog.ts` and `education.ts`. Tests: `src/__tests__/feedingLogs.test.ts`, `education.test.ts`. No migration: both tables (`feeding_logs`, `educational_contents`) already existed.

## Feeding logs — `/children/:childId/feeding-logs`

A caregiver or a linked professional records how many meals a child had on a day, plus an optional detail. Anyone with an active link can read them.

### `POST /children/:childId/feeding-logs`

| Field         | Type         | Required | Notes                                                       |
| ------------- | ------------ | :------: | ----------------------------------------------------------- |
| `id`          | UUID         |   yes    | Generated by the client; makes the request idempotent.      |
| `logDate`     | `YYYY-MM-DD` |   yes    | The day described. Not in the future, not before the birth. |
| `mealsPerDay` | integer      |   yes    | 0 to 12 (also a DB `CHECK`).                                |
| `details`     | string       |    no    | Up to 500 characters, trimmed; empty text is rejected.      |

Extra fields are rejected (`400`). Response: `{ id, childId, logDate, mealsPerDay, details }` (`details` is `null` when omitted).

| Status | Meaning                                                                                                                   |
| ------ | ------------------------------------------------------------------------------------------------------------------------- |
| `201`  | Created.                                                                                                                  |
| `200`  | The same `id` was already stored for this child (idempotent resend). Nothing is duplicated, even with concurrent resends. |
| `400`  | Invalid body or `childId`, future date, or date before birth.                                                             |
| `401`  | No valid token.                                                                                                           |
| `403`  | Missing permission, no active link (caregiver `cuida`, professional `atiende` today), or no active informed consent.      |
| `409`  | The `id` belongs to another child or to a log this user cannot see.                                                       |

Several logs for the same day are allowed (for example, one per caregiver); the app decides how to present them.

### `GET /children/:childId/feeding-logs?from=&to=&limit=`

Newest `logDate` first. `from` / `to` (`YYYY-MM-DD`, inclusive) are optional; `limit` is 1–365 (default 100). Reading stays possible after consent is revoked; only writing is blocked.

### Rules

- **Permissions** (`lib/permissions.ts`): `feedinglog:read` (existing) and the new `feedinglog:create`, granted to caregivers and to every professional specialty, like `checkup:create`. See [permissions.md](permissions.md).
- **Order of checks**: `authenticate` → `requirePermission` → `requireLink('childId')` → `requireActiveConsent('childId')` (POST only) → body validation. The service repeats the consent check inside the transaction.
- **RLS**: `feeding_logs` has the `child_access` policy (`app_has_child_access(child_id)`), so a user never reads or writes another child's logs. The insert is `createMany({ skipDuplicates })` (`ON CONFLICT (id) DO NOTHING`), which works under RLS.
- **Audit**: `POST` writes `CREATE` / `feeding_logs` with the log id; `GET` writes `READ` / `feeding_logs` with the child id (same as checkups).
- Logs are not immutable at database level (no trigger), but the API offers no edit or delete: a wrong entry is a new log. Add that endpoint if the app needs it.

### Offline decision (NK-39)

**Feeding stays out of the offline sync queue for now.** NK-27 keeps queueing only checkups and `POST /sync/checkups` (NK-28) only receives checkups.

- Checkups need the queue because a missing measurement cannot be re-created later and the server must recompute indicators and alerts. A feeding log is a small, low-risk record the caregiver can enter again.
- Generalizing the queue means a new entity type in the local store, a new batch endpoint and per-type conflict rules (NK-27/NK-28 scope).
- The endpoint is already safe to retry: the client-generated `id` makes `POST` idempotent. If a later iteration wants offline feeding, the app can queue these `POST`s and replay them one by one (a `POST /sync/feeding-logs` batch can be added then) **without any API or schema change**.

The app should therefore require a connection to save feeding for now and show a clear message when offline.

## Educational content — `GET /education`

Articles about feeding, in plain language, for an age in months and a language.

`GET /education?ageMonths=30&language=es`

| Query       | Type    | Default | Notes                                                                                                                                     |
| ----------- | ------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `ageMonths` | integer | —       | 0–240. Returns articles with `minAgeMonths <= ageMonths <= maxAgeMonths` (both inclusive). Without it, the whole catalog of the language. |
| `language`  | string  | `es`    | 2–3 letter code, lower-cased (`es`, `qu`).                                                                                                |

Response: array of `{ id, title, body, minAgeMonths, maxAgeMonths, language }`, ordered by age range then title. Any authenticated role (`401` otherwise); it is not child data, so there is no link, consent or permission check, and the table has no RLS.

The app computes the child's age in months (`ageInMonths` from `@nutrikids/who-growth` or the same rule on the phone) and passes it. The database keeps `min_age_months <= max_age_months` as a `CHECK`.

### Seed

`src/lib/seedEducation.ts` (run by `pnpm db:seed`, in every environment because it is reference content, not child data) loads **20 Spanish articles: 5 per age band** — 12–23, 24–35, 36–47 and 48–60 months, the range of the WHO references. Each has a fixed id and is written with `upsert`, so re-running never duplicates and fixing a text in the file fixes it in the database. Kichwa (`qu`) is not seeded: the Kichwa UI is still a machine-translated draft ([i18n.md](i18n.md)), and nutrition content must be reviewed by native speakers before it is added.

### Offline reading (NK-40)

The mobile local store (NK-27) saves children, checkups, results and curves, not content. Decision for the app:

1. Download the **whole catalog** of the user's language once (`GET /education?language=es`, no `ageMonths`: about 20 short articles) and store it locally (the local database or a JSON file); filter by age on the phone using `minAgeMonths` / `maxAgeMonths`.
2. Refresh when online. Express adds an `ETag` to the response, so sending `If-None-Match` answers `304` with no body when nothing changed.
3. If the catalog is empty and the phone is offline, show a "connect once to download" message.

No API change is needed for this; the article `id` is stable, so the phone can replace its copy by `id`.
