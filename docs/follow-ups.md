# Clinical Follow-ups (RF-15)

A linked professional records observations, recommendations, interventions and referrals for a child, optionally tied to one of the child's alerts. When the follow-up includes the date of the next checkup, the server creates the matching reminder in the same transaction.

Implemented in `src/services/followUps.service.ts` and `src/routes/children.routes.ts`; schemas in `packages/shared/src/schemas/followUp.ts`.

## Endpoint

`POST /children/:childId/follow-ups`

| Field             | Type                                                              | Required | Notes                                                    |
| ----------------- | ----------------------------------------------------------------- | :------: | -------------------------------------------------------- |
| `id`              | UUID                                                              |   Yes    | Generated by the client (idempotency, offline use).      |
| `groupId`         | UUID                                                              |    No    | Group identifier for consultation grouping (NK-75).      |
| `type`            | `observation` \| `recommendation` \| `intervention` \| `referral` |   Yes    | Matches the `follow_ups_type_check` constraint.          |
| `details`         | string (1–2000, trimmed)                                          |   Yes    |                                                          |
| `nextCheckupDate` | `YYYY-MM-DD`                                                      |    No    | Today or later (UTC). Creates the next-checkup reminder. |
| `alertId`         | UUID                                                              |    No    | Must be an alert of the same child.                      |

`professionalId` is taken from the session; extra fields are rejected.

### Response

`201` (created) or `200` (resend of an existing `id`) with:

```json
{
  "id": "…",
  "childId": "…",
  "groupId": null,
  "alertId": null,
  "professionalId": "…",
  "type": "recommendation",
  "details": "…",
  "nextCheckupDate": "2026-11-27",
  "reminder": {
    "id": "…",
    "childId": "…",
    "type": "next_checkup",
    "scheduledFor": "2026-11-27T13:00:00.000Z",
    "status": "pending"
  }
}
```

`reminder` is `null` when no `nextCheckupDate` was given.

## Batch Endpoint (NK-75)

`POST /children/:childId/follow-ups/batch`

Records 1 to 3 clinical follow-up items atomically linked under the same `groupId` in a single transaction.

| Field             | Type                                                              | Required | Notes                                                                                                              |
| ----------------- | ----------------------------------------------------------------- | :------: | ------------------------------------------------------------------------------------------------------------------ |
| `groupId`         | UUID                                                              |    No    | Explicit group id. When omitted, server derives it deterministically from `items[0].id`.                           |
| `alertId`         | UUID                                                              |    No    | Must be an alert belonging to the same child. Attached to all items.                                               |
| `nextCheckupDate` | `YYYY-MM-DD`                                                      |    No    | Today or later (UTC). Creates exactly one reminder attached to `items[0].id`.                                      |
| `items`           | Array of 1..3 `{ id: UUID, type: FollowUpType, details: string }` |   Yes    | Must contain at most one item per type (no duplicate types). Each `id` is generated by the client for idempotency. |

### Idempotency and Group ID Derivation

- **Group ID derivation:** If `groupId` is sent by the client, it is used. Otherwise, the server derives it deterministically as `items[0].id`. Replaying the same batch always yields the identical `groupId`.
- **Idempotency:** Resending the entire batch with the same `id`s returns the existing follow-ups with `200 OK` without duplicating records or reminders.
- **Atomicity:** If any item is invalid or if any item `id` already exists for another child, the entire operation is aborted and nothing is saved (`409 Conflict` or `400 Bad Request`).
- **Audit:** Each created follow-up row produces a distinct `CREATE` event in `audit_logs` (`entityType = 'follow_ups'`, `entityId = item.id`). Resending an existing batch does not duplicate audit entries.
- **Response:** Array of `FollowUpResponse` objects with `groupId`.

```json
[

    "groupId": "…",
    "alertId": "…",
```

## Reminder

- One row in `reminders` per follow-up with a next checkup: `type = 'next_checkup'`, `status = 'pending'`, linked by `reminders.follow_up_id` (unique, `ON DELETE CASCADE`).
- `scheduledFor` is the checkup date at 09:00 America/Caracas (13:00 UTC, `REMINDER_HOUR_UTC`).
- Resending the same follow-up `id` returns the existing follow-up and reminder; nothing is duplicated.

## Alerts

Referencing an alert does **not** change its status. After the follow-up exists, the professional moves the alert `REVIEWED → FOLLOW_UP_ESTABLISHED` with `PATCH /alerts/:alertId/status` (the `alerts_follow_up` trigger requires a follow-up with that `alert_id`). See [alerts.md](alerts.md).

## Access and errors

Requires the `PROFESSIONAL` role, the `followup:create` permission (nutrition, pediatrics), an active `atiende` link with the child and active informed consent. Audited as `CREATE` on `follow_ups`.

| Code  | Reason                                                                              |
| ----- | ----------------------------------------------------------------------------------- |
| `400` | Invalid body, next checkup date in the past, or the alert belongs to another child. |
| `401` | Missing or invalid token.                                                           |
| `403` | Caregiver, nursing, no active professional link, or no active consent.              |
| `404` | Referenced alert does not exist or is not visible.                                  |
| `409` | The `id` already belongs to a follow-up of another child.                           |

## Mobile form (NK-34, NK-75)

`apps/mobile/src/app/(professional)/follow-up.tsx` (route `/(professional)/follow-up?alertId=...&childId=...`, hidden from the drawer; opened from the alert detail with «Registrar seguimiento»). Design: Figma «Seguimiento clínico».

- **Fields**: three optional text sections — «Observaciones clínicas» (`observation`), «Intervención nutricional» (`intervention`) and «Derivación» (`referral`), each 1–2000 characters, with at least one section required — plus a common next checkup (`DD/MM/AAAA`, optional, never before today in UTC like the API; quick choices of 1 week, 2 weeks, 1 month and 3 months). Non-empty sections are submitted together as one atomic batch (`POST /children/:childId/follow-ups/batch`) sharing a client-generated `groupId` (`recommendation` remains supported in the schema and single follow-up endpoint).
- **Alert**: with an `alertId` the batch references it and a checkbox (on by default, hidden when the alert is already `FOLLOW_UP_ESTABLISHED`) moves the alert to «seguimiento establecido» once per batch after saving. The state machine has no shortcut, so an alert still `PENDING_REVIEW` goes through `REVIEWED` first (`establishAlert` in `lib/follow-up-sync.ts`). If only that step fails (for example a concurrent change) the follow-ups stay saved and the screen says the alert was not updated.
- **«Guardar como borrador»** keeps the multi-section form on the phone (one draft per user and alert, or per child), restores it when the form is opened again and drops it after a successful save or at sign-out. Legacy single-item drafts are migrated automatically (`recommendation` maps to the intervention section).
- **Without connection** (a request that gets no answer): the form shows «Sin conexión · Se guardará en este teléfono y se enviará al recuperar la conexión», saves the full batch in the local queue and goes back. The queue is flushed when the form or the alert detail gains focus (the alert detail shows how many batches are waiting). Item `id`s and `groupId` are created once per attempt, so a resend returns the existing follow-ups (`200`) instead of duplicating them. A queued batch that the server later refuses (4xx) goes back to the drafts with the server message so it can be corrected; 5xx/no connection stay queued.
- **Storage**: `lib/follow-up-storage.ts` keeps drafts and the batch queue in one encrypted SecureStore value, scoped by user, and migrates any legacy single-item queue entries without losing data. Sign-out clears the drafts but not the queued follow-ups, so nothing waiting is lost.
- **Limits**: there is no connectivity listener yet, so «offline» is detected when a request fails and the queue is flushed on focus, not at the instant the connection returns. NK-27 (SQLite and the general sync queue) and NK-29 (connection indicator) should replace `follow-up-storage.ts` and the focus trigger; callers only use `submitFollowUp` / `flushPendingFollowUps`.
