# Clinical Follow-ups (RF-15)

A linked professional records observations, recommendations, interventions and referrals for a child, optionally tied to one of the child's alerts. When the follow-up includes the date of the next checkup, the server creates the matching reminder in the same transaction.

Implemented in `src/services/followUps.service.ts` and `src/routes/children.routes.ts`; schemas in `packages/shared/src/schemas/followUp.ts`.

## Endpoint

`POST /children/:childId/follow-ups`

| Field             | Type                                                              | Required | Notes                                                    |
| ----------------- | ----------------------------------------------------------------- | :------: | -------------------------------------------------------- |
| `id`              | UUID                                                              |   Yes    | Generated by the client (idempotency, offline use).      |
| `type`            | `observation` \| `recommendation` \| `intervention` \| `referral` |   Yes    | Matches the `follow_ups_type_check` constraint.          |
| `details`         | string (1–2000, trimmed)                                          |   Yes    |                                                          |
| `nextCheckupDate` | `YYYY-MM-DD`                                                      |    No    | Today or later (UTC). Creates the next-checkup reminder. |
| `alertId`         | UUID                                                              |    No    | Must be an alert of the same child.                      |

`professionalId` is taken from the session; extra fields are rejected.

### Response

`201` (created) or `200` (resend of an existing `id`) with:

```json
{
  "id": "…",
  "childId": "…",
  "alertId": null,
  "professionalId": "…",
  "type": "recommendation",
  "details": "…",
  "nextCheckupDate": "2026-11-27",
  "reminder": {
    "id": "…",
    "childId": "…",
    "type": "next_checkup",
    "scheduledFor": "2026-11-27T13:00:00.000Z",
    "status": "pending"
  }
}
```

`reminder` is `null` when no `nextCheckupDate` was given.

## Reminder

- One row in `reminders` per follow-up with a next checkup: `type = 'next_checkup'`, `status = 'pending'`, linked by `reminders.follow_up_id` (unique, `ON DELETE CASCADE`).
- `scheduledFor` is the checkup date at 09:00 America/Caracas (13:00 UTC, `REMINDER_HOUR_UTC`).
- Resending the same follow-up `id` returns the existing follow-up and reminder; nothing is duplicated.

## Alerts

Referencing an alert does **not** change its status. After the follow-up exists, the professional moves the alert `REVIEWED → FOLLOW_UP_ESTABLISHED` with `PATCH /alerts/:alertId/status` (the `alerts_follow_up` trigger requires a follow-up with that `alert_id`). See [alerts.md](alerts.md).

## Access and errors

Requires the `PROFESSIONAL` role, the `followup:create` permission (nutrition, pediatrics), an active `atiende` link with the child and active informed consent. Audited as `CREATE` on `follow_ups`.

| Code  | Reason                                                                              |
| ----- | ----------------------------------------------------------------------------------- |
| `400` | Invalid body, next checkup date in the past, or the alert belongs to another child. |
| `401` | Missing or invalid token.                                                           |
| `403` | Caregiver, nursing, no active professional link, or no active consent.              |
| `404` | Referenced alert does not exist or is not visible.                                  |
| `409` | The `id` already belongs to a follow-up of another child.                           |
