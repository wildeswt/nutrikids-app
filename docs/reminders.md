# Reminders (NK-37, RF-16)

Reminders tell caregivers about upcoming checkups and activities, in the app (internal notification) and as a push notification. A server job sends them ahead of their date.

## Where reminders come from

| Source                             | `type`         | Created by                                                                            |
| ---------------------------------- | -------------- | ------------------------------------------------------------------------------------- |
| Follow-up with `nextCheckupDate`   | `next_checkup` | The server, in the same transaction as the follow-up ([follow-ups.md](follow-ups.md)) |
| A caregiver or linked professional | `checkup`      | `POST /reminders`                                                                     |
| A caregiver or linked professional | `activity`     | `POST /reminders`                                                                     |

Status: `pending` → `sent` (the job notified the caregivers) → `completed` (the user marked it done). A `completed` reminder is never sent.

## Endpoints

All require a bearer token. Row access is decided by RLS (`child_access`): a caregiver of the child or a professional with an active link. Anything else is invisible (empty list or `404`).

| Method and path                 | Description                                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `GET /reminders`                | Lists reminders, soonest first (max 200). Optional `?childId=` and `?status=pending\|sent\|completed`. |
| `POST /reminders`               | Creates one. Body `{ id, childId, type: 'checkup' \| 'activity', scheduledFor }`.                      |
| `PATCH /reminders/:id/complete` | Marks it `completed`. Idempotent.                                                                      |

`POST /reminders` rules:

- `id` is generated by the client; resending the same `id` for the same child returns `200` with the existing reminder (no duplicate). The same `id` for another child is `409`.
- `scheduledFor` is an ISO 8601 instant with offset and must be in the future (`400` otherwise).
- The user must be linked to the child (`403`) and the child must have an active consent (`403`).
- `next_checkup` is reserved for the server; the body is strict, so extra fields (such as `status`) are rejected.

## Scheduled job

`startBackgroundJobs()` (`jobs/overdue-alerts.ts`) runs `runRemindersJob()` 30 s after start and then on the same interval as the overdue-alerts job (`OVERDUE_ALERTS_INTERVAL_MINUTES`, 60 by default).

Each pass calls the SQL function `dispatch_due_reminders(lead_hours)` (migration `20261114140000_due_reminders_function`). In a single statement it:

1. Marks as `sent` every `pending` reminder with `scheduled_for <= now() + lead_hours`.
2. Inserts one `reminder_due` notification (`entity_type = 'reminder'`) per caregiver of the child.

Because it is a single atomic statement, two concurrent passes cannot notify twice. The function is `SECURITY DEFINER` because the job runs without a session user and RLS would otherwise hide every row. After that, the API sends a push notification to the registered devices of those caregivers; push failures are logged and never undo the notification.

A reminder created when it is already inside the window (for example, one for tomorrow with a 24 h lead) is notified on the next pass.

## Configuration

| Variable              | Default | Meaning                                                           |
| --------------------- | ------- | ----------------------------------------------------------------- |
| `REMINDER_LEAD_HOURS` | `24`    | How many hours before `scheduledFor` the caregivers are notified. |

## Who detects overdue alerts

Decided: overdue **alerts** are detected by the NK-36 job (`find_overdue_alert_recipients`, see [notifications.md](notifications.md)), not by this one. Both jobs share the same timer, but each has its own SQL function and its own notifications.

## Known limits

- Caregiver devices do not register push tokens yet (the app only registers them for professionals), so for caregivers the push step is a no-op until that is added. The in-app `reminder_due` notification is created regardless and is readable at `GET /notifications`.
- Reminders cannot be edited or deleted, only completed.
