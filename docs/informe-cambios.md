## 2. RT-01 y RT-02: de PWA a aplicación móvil nativa (criterio de NK-48)

La decisión del equipo es una aplicación móvil nativa con React Native (Expo), no una aplicación web progresiva. En el repositorio: `apps/mobile` usa Expo Router, `expo-secure-store` para las credenciales y `expo-notifications` para el push; no hay `service worker` ni manifiesto web.

### RT-01 (Tabla 3, p. 27)

|                            | Texto                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Hoy**                    | "Aplicación web progresiva instalable y adaptable a pantalla de teléfono, tableta y computador, con un solo código base." Justificación: "Una aplicación web progresiva es independiente de la plataforma y puede operar con y sin conexión (Hannan Bin Azhar y Mohan, 2022)."                                                                                 |
| **Debe decir**             | "Aplicación móvil nativa para Android e iOS, desarrollada con React Native y Expo con un solo código base, y con interfaz adaptable a teléfono y tableta."                                                                                                                                                                                                     |
| **Justificación sugerida** | "Un solo código base sirve a dos plataformas móviles y da acceso directo a las notificaciones push y al almacenamiento seguro del dispositivo (Keychain en iOS, Keystore en Android), que una aplicación web no ofrece con la misma fiabilidad." No inventar citas: si se quiere sustentar con literatura, buscar una fuente sobre desarrollo multiplataforma. |
| **Consecuencia**           | La referencia Hannan Bin Azhar y Mohan (2022) (p. 49) queda sin citar: eliminarla de las Referencias, o citarla en el texto como alternativa descartada (una PWA).                                                                                                                                                                                             |

## 4. Requerimientos tecnológicos cuyo estado real difiere

Los demás RT coinciden con el código: RT-03 (API REST; HTTPS depende del despliegue), RT-04 (PostgreSQL 16), RT-05 (permisos por rol y vínculo en el servidor, `docs/permissions.md`), RT-09 (notificaciones internas y push con tareas programadas, `docs/notifications.md`, `docs/reminders.md`) y RT-11 (respaldos cifrados con política de conservación, `docs/backups.md`).

### RT-06, autenticación (p. 28)

- **Coincide:** contraseñas con hash **Argon2id**, sesión con token de acceso de 15 minutos y token de renovación rotativo de 30 días, y registro de profesionales con **código de invitación** y número de registro profesional único (`docs/auth.md`).
- **Falta en el informe:** el **límite de intentos de inicio de sesión** (5 fallidos cada 15 minutos por IP y correo, luego `429`; variables `LOGIN_MAX_ATTEMPTS` y `LOGIN_WINDOW_MINUTES`). Conviene mencionarlo porque la prueba PSEG-02 lo ejercita.
- **No coincide:** "verificación en dos pasos para profesionales". La base de datos tiene las columnas (`totp_secret_enc`, `totp_enabled_at`, `recovery_code_hashes`) y la pantalla de inicio de sesión tiene el paso, pero la API responde siempre `requiresTwoFactor: false` (`apps/api/src/services/auth.service.ts`); no hay forma de activarla. Redactar como "prevista" o implementarla antes de la entrega.

### RT-07, cifrado y pseudonimización (p. 28; Tabla 5, p. 34)

- **No coincide:** el informe afirma "cifrado de los datos de salud en reposo y pseudonimización de los identificadores en cualquier exportación" y, en la Tabla 5, "cifrado de columna en nombres, apellidos y teléfono". El código **no cifra columnas** (tarea NK-43, estado _Todo_) y la única exportación (`GET /children/:childId/export`, derechos del representante) devuelve los datos del propio niño al representante, no una exportación estadística, por lo que no hay seudonimización.
- **Protecciones que sí existen** y pueden citarse: seguridad por filas en PostgreSQL, contraseñas con Argon2id, copias de respaldo cifradas con AES-256 (`scripts/backup`), tablas inmutables y auditoría. El cifrado del volumen depende del proveedor donde se despliegue; no está en el repositorio.
- **Acción:** implementar NK-43 o redactar RT-07 y la fila "Cifrado" de la Tabla 5 como pendientes.

### RT-08, referencia LMS y biblioteca de cálculo (p. 28)

- **Coincide:** las tablas LMS de la OMS están en la tabla `lms_references` y el cálculo vive en un paquete compartido del monorepo (`packages/who-growth`).
- **No coincide del todo:** el informe dice "una misma biblioteca de cálculo para cliente y servidor". Hoy solo el servidor usa `who-growth` (la aplicación móvil no lo importa): calcula el servidor y la aplicación muestra el resultado y dibuja las curvas con `GET /reference/curves`. El cálculo en el dispositivo sin conexión no existe (depende de la cola de RT-02).

### RT-10, idioma (p. 28)

- **Coincide:** interfaz en español con estructura de traducciones por clave (`docs/i18n.md`).
- **Matizar:** el kichwa (`qu`) existe como **borrador traducido automáticamente**, pendiente de revisión por hablantes nativos. El informe no debe presentarlo como idioma disponible.

## 8. Diseño de pruebas (Tabla 8, pp. 45-46)

El plan define casos PU, PI, PS, PSEG, PPRI, PUS y PA. Conviene que el informe pase de "esperado" a "ejecutado":

- La suite automatizada (`pnpm test`) cubre los niveles unitario, de integración, de sistema, de seguridad y de privacidad con datos sintéticos (el seed usa dominios `example.test`; ninguna prueba usa datos reales de niños).
- La matriz que relaciona cada RF y RT de prioridad alta con su prueba y el resultado de la ejecución se entrega con NK-46 (pruebas de sistema y de seguridad). Una vez fusionada, agregar a la Tabla 8 una columna "Prueba automatizada" y "Resultado".
- Las pruebas de usabilidad (PUS-01, escala SUS) y de aceptación (PA-01) requieren usuarios y no son automatizables: siguen pendientes, y NK-47 las cubre.
